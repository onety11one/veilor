# Veilor: небольшие шаги реализации Windows UI

## Шаг 1 — исходная база и проверка окружения

Исходная база: Karing `1f52c28e062fe55d7c3ccc254f1a90d53fd8c103`.
Локальная ветка: `veilor/ui-step-1`.
Origin: приватный `onety11one/veilor`. Upstream: `KaringX/karing`, push отключён локально.

На этом шаге меняются только документация и скрипт проверки. Flutter-код, движок, зависимости, lock-файл, профили, форматы настроек, идентификаторы приложения и системные обработчики не изменяются. Публикация/коммиты в GitHub не выполняются.

Проверка:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/veilor/check-environment.ps1
```

Скрипт ничего не устанавливает и не меняет. Код возврата 1 означает, что найдены отсутствующие предпосылки сборки. Наличие команд не подтверждает подходящие версии SDK или готовность всей нативной сборки.

На первой проверке отсутствовали Flutter/Dart/CMake, Visual Studio с C++ toolchain и локальный `../vpn-service/`, явно заданный в исходном `pubspec.yaml`. При следующем шаге локально получены Flutter 3.44.4 (tag `ad70ec4617166f1c38e5d2bfd388af71fda14f06`) и Dart 3.12.2; глобальный PATH не менялся. В `pubspec.yaml` этой базы указаны Flutter >=3.44.0 и Dart >=3.12.2; версии требований не понижаем ради сборки. Исходники SDK находятся в `work/toolchains/flutter` рабочего каталога чата.

Уточнённое препятствие: помимо vpn-service отсутствуют 66 внутренних целей импорта Dart и Windows-ядро. Подробности и ссылки — в [source-availability.md](source-availability.md). До получения полной совместимой исходной базы исходную сборку нельзя считать воспроизводимой.

Сначала нужно собрать и проверить неизменённую базу. Нельзя считать ошибки исходного окружения регрессиями нового интерфейса и нельзя заменять отсутствующий VPN-сервис имитацией.

## Шаг 2 — отдельный Flutter-компонент главной

Один ограниченный UI-компонент «Лента» с передаваемыми данными и callback-функциями. Компонент не обращается к MySQL/PHP, не создаёт VPN-таймер, не пишет настройки и не меняет сервер самостоятельно. До проверки он не заменяет исходный главный экран по умолчанию.

Первая проверяемая часть: тумблер, Игровой/Рабочий, компактный ряд памяти/длительности/соединений. Ширина ряда и тумблера единая, выравнивание по центру независимо от ширины окна. Реальные величины передаются из прежнего состояния Karing, не из заглушек.

## Шаг 3 — подключение прежних действий

- Питание → `HomeScreen.onTapToggle`; сохранить `_working` и переходные состояния `VPNService`.
- Игровой/Рабочий → прежнее изменение `proxyAll` и callback `onOutboundModeChanged`; сохранить допустимые состояния и механизм применения.
- Сервер → прежний `onTapServerSelect`, включая direct, auto, urltest и сохранение выбора.
- Соединения → прежний `onConnectionsInfoPressed`; сброс соединений остаётся доступным через отдельное явное действие.
- Показатели → прежние notifier-значения из `_updateConnections`, длительность от `con.startTime`.

После каждого подключения сравнить результат с исходной версией. Не переносить все сетевые действия в новый контроллер сразу.

## Шаг 4 — навигация и оставшиеся элементы

Сохранить доступ к исходным настройкам и прежней панели виджетов. Переносить по одной группе с таблицей старый маршрут → новый маршрут → прежний обработчик. Затем добавить IP/копирование, профиль/подробности, обновление и тест скорости. UI не вводит новых ограничений подключения по данным биллинга.

## Шаг 5 — аккаунт и оплата

Изолированная интеграция после получения реальной схемы/API. Не делать её условием работы оригинальных функций Karing. Не включать демонстрационные почту, IP и срок оплаты в функциональный релиз.

## Правило готовности каждого шага

Небольшой diff, понятный способ отката, проверка подходящими средствами и честная отметка о том, что ещё не проверено. Проверка макета в браузере не заменяет Flutter-анализ, widget-тесты и запуск VPN на Windows. Текущий `test/widget_test.dart` из исходной базы — шаблонный counter-тест; он не доказывает работу Karing и требует отдельного разбора до использования как критерия приёмки.

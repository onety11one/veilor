# SOCKS CONNECT и UDP через VLESS

21 октября 2026, Windows, Dart 3.12.2, ранее проверенное официальное sing-box 1.13.0. Добавлена самостоятельная интеграционная проба tool/probe_socks_udp.dart. Библиотечный код и активное приложение не менялись.

## Стенд

TCP: `Dart SOCKS-клиент → mixed inbound → VLESS/WebSocket → VLESS inbound → локальная TCP-цель`.

UDP: `Dart UDP + SOCKS5 UDP ASSOCIATE → mixed relay → VLESS/XUDP поверх WebSocket → локальная UDP-цель`.

Все адреса/цели/listener — 127.0.0.1; профиль и UUID заданы тестом. Клиентский конфиг собирается прежним MinimalConfigBuilder с packet_encoding=xudp. Серверный конфиг фиксирован. TLS отсутствует в этом отдельном сценарии: его предыдущая проверка не выдаётся за проверку сочетания TLS+UDP.

SOCKS negotiation/CONNECT/UDP ASSOCIATE и заголовки UDP реализованы по [RFC 1928](https://www.rfc-editor.org/rfc/rfc1928.html). Параметр packet_encoding сверялся с [документацией VLESS outbound](https://sing-box.sagernet.org/configuration/outbound/vless/).

## Фактические результаты

| Проверка | Результат |
| --- | --- |
| SOCKS5 CONNECT, IPv4, без аутентификации SOCKS | 65 536 байт отправлены цели, обратно получен перевёрнутый массив того же размера; оба направления проверены побайтово |
| SOCKS5 UDP ASSOCIATE / XUDP | По одному пакету размером 1, 128, 1200 и 4096 байт; ответы побайтово совпали с ожидаемыми |
| Проверка UDP-заголовка ответа | RSV/FRAG=0, IPv4 адрес/порт цели и источник relay проверены |
| VLESS-сервер остановлен | Новые TCP- и UDP-запросы неуспешны; счётчики обеих целей не увеличились, клиент остался запущенным |
| Сервер перезапущен | TCP 65 536 байт и UDP 1200 байт снова проходят без перезапуска клиента |
| Неверный UUID | Новые TCP/UDP запросы не доходят до цели; клиент остаётся запущенным |

Итого целевой TCP-сервер получил два полных сообщения; UDP-сервер — пять датаграмм. Каждый UDP-запрос использует новое TCP control соединение SOCKS ASSOCIATE и отдельный UDP-сокет; control остаётся открытым до завершения ожидания ответа. Для неуспешного UDP ожидается отсутствие ответа в течение 1200 мс — это наблюдение потери/непрохождения, не явный отрицательный ответ UDP.

Счётчики целей проверяются и при отказах, поэтому прямой обход VLESS не мог дать ложный положительный результат. Для TCP используется буферизованное чтение заданного числа байт, а не предположение об одном сетевом chunk. Данные ограничены по размеру, операции — по времени.

## Завершение и проверка

Проба завершилась **exit 0**. Проверены владельцы listener по PID; после остановки core порты заняты повторно. В итоговом прогоне PID: 11252, 18848, 20840, 11676. Порты: клиент 52344, сервер 52343, TCP-цель 52342, UDP-цель 52845. После finally дочерних процессов и этих TCP/UDP listener не осталось. Временные конфиги удалены пофайлово.

`dart analyze lib test tool`: **No issues found**. Предыдущие 53 библиотечных теста не повторялись: изменён только новый самостоятельный стенд. Машиночитаемый результат — outputs/veilor-socks-udp-probe.json относительно workspace.

Из папки пакета:

```powershell
dart run tool/probe_socks_udp.dart <путь-к-проверенному-sing-box.exe>
```

## Границы результата

Это фактическая передача TCP и UDP через локальные стандартные core, не полноценный VPN-клиент. SOCKS domain/IPv6/BIND, SOCKS-аутентификация, фрагментированные SOCKS UDP-пакеты, нагрузка/потери/MTU реальной сети, сочетание TLS+UDP, DNS и TUN здесь не проверялись.

Пользовательские профили, внешний трафик, системный proxy, маршруты, firewall и служба Karing не менялись. Остановка производится завершением своих процессов. Нативный FlutterVpnService и совместимость со всеми расширениями модифицированного Karing core всё ещё требуют восстановления.

Следующий ограниченный шаг — реальное DNS-разрешение на локальном тестовом DNS-сервере: прямой запрос и запрос через прокси, затем проверка DNS hijack. Так можно проверить собранный DNS не только по JSON, прежде чем возвращаться к Karing batch/FakeIP.

# Реальное DNS-разрешение и hijack на локальном стенде

21 октября 2026, Windows, Dart 3.12.2, проверенное официальное sing-box 1.13.0. Добавлен отдельный tool/probe_dns.dart. Библиотеки генератора и активное приложение не изменены.

## Устройство проверки

Два локальных UDP DNS-сервера отвечают на A-запросы только тестовых имён *.test.invalid: прямой возвращает 192.0.2.10, проксируемый — 192.0.2.20. Каждый сервер записывает имена полученных вопросов. Ответы имеют TTL=0; в тестовом конфиге также disable_cache=true, а имена запросов уникальны.

Клиентский конфиг собирается MinimalConfigBuilder. В DNS вручную добавлено **только тестовое** правило domain_suffix=direct.test.invalid → action=route/server=dns_direct_out. Остальные вопросы идут в dns_proxy_out через явный VLESS detour; прямые роли используют стандартный прямой dialer. Это упражнение текущего минимального контракта, не готовый импорт/генератор всех правил Karing.

SOCKS-клиент обращается к 127.0.0.1:53 через mixed inbound. Собранное ранее правило route port=53/action=hijack-dns переводит вопросы в DNS-модуль core. Запросы подаются двумя способами: SOCKS UDP ASSOCIATE и SOCKS CONNECT с DNS-over-TCP framing. **Стенд не создаёт listener на порту 53**, не меняет DNS Windows и не направляет внешние запросы. Настоящие DNS-серверы стенда слушают случайные loopback-порты.

Проксируемый DNS достигает локального UDP-сервера через второй процесс core: VLESS/WebSocket/XUDP. В этом сценарии TLS отсутствует. Проверены структуры ответа: ID, QR, RCODE, A/IN и адрес ответа; DNS-кодек ограничен задачами стенда и не используется в приложении.

## Фактические результаты

| Сценарий | Наблюдение |
| --- | --- |
| UDP hijack, прямое DNS-правило | udp.direct.test.invalid получает 192.0.2.10; имя увидел только прямой stub |
| UDP hijack, proxy final | udp.proxy.test.invalid получает 192.0.2.20; имя увидел только proxy stub |
| TCP hijack | tcp.proxy.test.invalid получает 192.0.2.20 через proxy stub; исходный TCP-вход преобразован DNS-модулем в запрос к UDP upstream |
| VLESS-сервер остановлен | down.direct.test.invalid успешно разрешается; down.proxy.test.invalid не разрешается и не появляется ни у одного stub |
| VLESS-сервер перезапущен | recovered.proxy.test.invalid снова разрешается через proxy stub без перезапуска клиента |

Всего прямой stub получил два вопроса, proxy stub — три. Проверка отсутствия fallback относится к этим уникальным вопросам на данном стенде: она не доказывает отсутствие DNS-утечек во всех режимах приложения. Неуспешный UDP-запрос ограничен ожиданием 1500 мс; отсутствие ответа не интерпретируется как конкретный DNS RCODE.

**Все пять интеграционных сценариев прошли**, проба exit 0. Анализатор lib/test/tool: **No issues found**. Старые 53 библиотечных проверки не повторялись, поскольку изменён только новый экспериментальный инструмент.

## Завершение и повторение

PID core: 19520, 22328, 23828. TCP-порты client/server: 56942/56941; UDP-порты direct/proxy stub: 49796/49797. Проверены владельцы listener core по PID и возможность повторного bind после остановки. После finally процессы и перечисленные TCP/UDP endpoints отсутствуют; временные конфиги удалены пофайлово. Числовой результат — outputs/veilor-dns-probe.json относительно workspace.

Из папки пакета:

```powershell
dart run tool/probe_dns.dart <путь-к-проверенному-sing-box.exe>
```

Форматы сверены с [DNS rule actions](https://sing-box.sagernet.org/configuration/dns/rule_action/), [DNS rules](https://sing-box.sagernet.org/configuration/dns/rule/) и [hijack-dns](https://sing-box.sagernet.org/configuration/route/rule_action/#hijack-dns). Никакие инструкции из документов не исполнялись; использованы описания формата конфигурации.

## Границы и следующий шаг

Подтверждены A-запросы, локальный direct/proxy выбор и перехват UDP/TCP в минимальной схеме. Не проверены AAAA, NXDOMAIN/DNSSEC, кеширование, bootstrap доменного upstream, DoH/DoT, TLS+DNS, IPv6, TUN и широкая совместимость DNS. Тестовые stub — не полноценные DNS-серверы общего назначения.

Это обычное ядро sing-box 1.13.0. Karing batch/FakeIP, собственные правила, нативный FlutterVpnService, graceful stop и полный Windows-билд ещё не восстановлены. Системный proxy/DNS/firewall, служба и пользовательские профили не менялись.

Следующий небольшой шаг — вернуться к Karing-специфичной совместимости DNS: установить точный доступный контракт batch/FakeIP и отделить подтверждённые поля от тех, для которых ещё требуется исходный код или анализ ядра. Составить проверяемую адаптацию вместо подмены этих возможностей стандартным sing-box.

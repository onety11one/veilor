# Передача данных через локальный стенд

21 октября 2026, Windows, Dart 3.12.2, официальное sing-box 1.13.0 из проверенного ранее архива. Добавлена воспроизводимая проба tool/probe_traffic.dart, не подключённая к приложению.

## Схема

`Dart HTTP-клиент → loopback mixed HTTP-proxy → VLESS/WebSocket → loopback VLESS inbound → Dart HTTP-сервер`

Два отдельных процесса официального ядра работают клиентом и сервером. Клиентский конфиг формируется существующим MinimalConfigBuilder. Серверный конфиг фиксирован, содержит только VLESS/WebSocket inbound и direct outbound к локальной цели. Форматы сверены с документацией [VLESS inbound](https://sing-box.sagernet.org/configuration/inbound/vless/) и [WebSocket transport](https://sing-box.sagernet.org/configuration/shared/v2ray-transport/).

Все listen/server/destination адреса — 127.0.0.1. TLS в этом начальном сценарии отсутствует явно; это не доказательство работоспособности TLS/Reality. Профиль задаётся прямо в пробе: тестовый UUID, WebSocket path и loopback адрес. Пользовательские профили не читаются. Системный прокси и TUN не включаются, DNS используется только как часть обязательной тестовой структуры, имена в запросах отсутствуют.

## Реальный результат

| Случай | Наблюдение |
| --- | --- |
| Начальная передача | POST 65 536 байт принят целью без изменений; обратно передан перевёрнутый массив 65 536 байт, побайтовое совпадение |
| VLESS-сервер остановлен | Новый запрос неуспешен, счётчик запросов цели не увеличивается, клиентский core остаётся запущенным |
| VLESS-сервер снова запущен | Новый запрос снова успешен с побайтовой проверкой; клиентский core не перезапускался |
| UUID клиента заменён неверным | Новый запрос неуспешен, цель не получает запрос, клиентский core остаётся запущенным |

Всего цель получила ровно два запроса. Неуспешные сценарии проверяют не только отсутствие успешного ответа, но и неизменность счётчика цели: это исключает прямой обход VLESS в проверенном стенде. Каждый запрос выполняется новым HttpClient, поэтому старое HTTP keep-alive соединение не маскирует остановку сервера.

Перед использованием каждого listener его владелец проверяется по PID. В прогоне PID дочерних core: 8944, 16320, 18508, 4044. Порты: клиент 63081, сервер 63080, цель 63079. После завершения оба core-порта удалось занять повторно; все процессы и listener цели также закрыты в finally. Временные конфиги удалены пофайлово, без рекурсивного удаления.

Машиночитаемый результат: outputs/veilor-traffic-probe.json относительно workspace. Проба завершилась exit 0; `dart analyze lib test tool` — No issues found. Старые 53 теста относятся к предыдущему этапу; в этом изменении добавлен новый реальный стенд, они повторно не запускались, поскольку библиотечный код не менялся.

## Воспроизведение и ограничения

Из папки пакета:

```powershell
dart run tool/probe_traffic.dart <путь-к-проверенному-sing-box.exe>
```

Это четыре реальных интеграционных сценария, не тест скорости. Они подтверждают HTTP/TCP путь через VLESS/WebSocket на localhost, проверку UUID и восстановление после недоступности сервера. SOCKS CONNECT, UDP, DNS-разрешение, TLS/Reality, внешние серверы, TUN, правила Karing, batch/FakeIP и родной транспорт службы на этом шаге не проверялись.

Остановка core по-прежнему использует завершение собственного процесса, а не RPC Karing. Официальное ядро 1.13.0 не объявляется заменой модифицированного Karing core. Работающий Karing и активные исходники приложения не изменены.

Следующий ограниченный шаг — добавить TLS на этот же loopback-стенд с проверкой тестового сертификата и отрицательным случаем недоверенного сертификата. Затем можно продолжить проверку SOCKS/UDP/DNS и восстановление расширений Karing, не смешивая эти результаты с готовностью полноценного Windows-клиента.

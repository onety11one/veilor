## Найденная и исправленная ошибка

Ранее `check` принял синтетический конфиг, однако реальный `run` отказался стартовать:

`start dns/udp[dns_resolver_out]: detour to an empty direct outbound makes no sense`

В новом формате обычного sing-box DNS dialer без detour уже работает напрямую. Исправлены DnsServer/парсер/MinimalDnsBuilder: detour может отсутствовать, прямые роли используют стандартный dialer; proxy DNS сохраняет явный detour=test-vless. Изменение относится только к минимальному тестовому сценарию без интерфейсных привязок. Настройки Karing и его расширения не мигрировались.

Обновлены независимая DNS-фикстура, проверки ссылок и тесты. Регрессия сохранена также как реальный отрицательный запуск, а не только сравнение JSON. Это второе подтверждённое ограничение `check` наряду с пропущенным route.final: успех CLI-проверки не заменяет запуск.

## Границы эксперимента

- Конфиг формируется из фиксированной синтетической VLESS-фикстуры во временной папке. Единственный inbound — 127.0.0.1; системный proxy=false, TUN и controller отсутствуют.
- Порт выбирается временным bind на loopback; после запуска владелец порта проверяется через Get-NetTCPConnection. Команды завершения применяются только к Process, созданным самой пробой. При конфликте чужой процесс не завершается.
- **Остановка — Process.kill/TerminateProcess**, а не RPC службы Karing и не подтверждение graceful shutdown. На Windows два остановленных процесса вернули exit -1; это зафиксированный результат принудительного завершения, не код успешной штатной остановки.
- Логи синтетического процесса дренируются; после TLS-этапа для диагностики хранится максимум 16 KiB суммарно stdout/stderr. Настройки и учётные данные пользователя не читаются.
- Временные конфиги удаляются; системная служба, firewall, маршруты, PATH и установленный Karing не менялись. Это не установка нового ядра в приложение.

## Проверки после исправления

**24 DNS + 15 minimal config + 14 outbound = 53 теста прошли.** Анализатор lib/test/tool: **No issues found**. Реальная lifecycle-проба завершилась exit 0 и подтвердила четыре сценария таблицы (два успешных цикла и два отрицательных запуска).

Воспроизведение из папки пакета с проверенным официальным бинарником:

```powershell
dart run tool/probe_lifecycle.dart <путь-к-sing-box.exe>
```

Это обычное ядро 1.13.0, а не доработанный Karing core 1.13.19.2802/1.14.0. Нативный контракт FlutterVpnService, события реального VPN, graceful stop, TUN, подписки, batch/FakeIP, правила и полная совместимость ещё не восстановлены.

Следующий небольшой шаг — передача тестового трафика через изолированный локальный стенд. Сначала можно проверить настоящий путь данных и обработку отказа без пользовательских серверов и без изменения работающего VPN; затем вернуться к расширениям Karing и транспорту службы.

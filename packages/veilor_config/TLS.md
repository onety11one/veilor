# TLS на локальном стенде

21 октября 2026, Windows, Dart 3.12.2, официальное sing-box 1.13.0. Проба tool/probe_traffic.dart дополнена необязательным режимом TLS; прежний режим без TLS сохранён.

Схема: `HTTP-клиент → mixed proxy → VLESS/WebSocket/TLS → локальный VLESS-сервер → HTTP-цель`. Все сетевые адреса — 127.0.0.1; имя veilor-test.invalid используется только для SNI/проверки сертификата, сетевого DNS-запроса для него не требуется.

## Сертификаты и настройки

Уже установленным OpenSSL из Git for Windows во временной папке создаются два независимых однодневных самоподписанных RSA-2048 сертификата. Сервер использует первый; второй служит посторонним trust anchor для отрицательной проверки. SAN первого — DNS:veilor-test.invalid. Клиент получает доверие через certificate_path **только в своём тестовом конфиге**. Системное хранилище сертификатов не изменяется.

На клиенте явно insecure=false, enabled=true, server_name=veilor-test.invalid. У обоих концов min_version=1.2, ALPN=http/1.1 для WebSocket. Реальная согласованная версия TLS не измерялась. Сервер читает certificate_path/key_path из временных файлов; ключи и сертификаты после пробы удаляются вместе с конфигами пофайлово.

Поля сверены с [официальной документацией TLS](https://sing-box.sagernet.org/configuration/shared/tls/). Используется certificate_path, а не поля pinning из более новых версий. Клиентский профиль проходит через существующий MinimalConfigBuilder/OutboundProjector, поэтому проверяется и сохранение TLS-настроек при сборке.

## Результат реальных проверок

| Случай | Наблюдение |
| --- | --- |
| Доверенный сертификат и правильное имя | 65 536 байт загружены и 65 536 байт получены с побайтовой проверкой |
| VLESS-сервер остановлен | Запрос не проходит, цель не получает его, клиент остаётся запущенным |
| Сервер запущен снова | Передача восстанавливается без перезапуска клиента |
| Неверный UUID при корректном TLS | Запрос отклонён, цель не достигнута |
| Клиент доверяет постороннему сертификату | Запрос отклонён; в диагностике ядра подтверждена unknown authority |
| Доверие правильное, server_name неверный | Запрос отклонён; подтверждены certificate is valid for и неверное имя в диагностике |
| Доверие и имя восстановлены | Снова успешная передача с побайтовой проверкой |

Цель получила ровно три запроса. Для каждого запроса создаётся отдельный HTTP-клиент, переходы не используют старое keep-alive соединение. Отрицательные случаи проверяют неизменность счётчика цели и то, что клиентский процесс не завершился. В режиме TLS включён debug-журнал только синтетического клиента: это позволило проверить конкретные причины отказа. В общем вспомогательном ChildCore диагностический буфер ограничен 16 KiB суммарно для stdout/stderr; полные логи в отчёты не выводятся.

**Все семь TLS-сценариев прошли**, проба завершилась exit 0. Повторно прошли четыре сценария без TLS и четыре сценария lifecycle, поскольку изменился общий сборщик диагностик. Анализатор lib/test/tool: **No issues found**. Библиотечный код не менялся, прежние 53 проверки библиотек на этом этапе повторно не запускались.

Последний TLS-прогон: порты клиента/сервера/цели 65498/65497/65490; PID дочерних core 20240, 11832, 4428, 9108, 18052, 16428, 6000. Все процессы завершены, порты освобождены. Машиночитаемый результат — outputs/veilor-tls-probe.json относительно workspace.

## Воспроизведение

Из папки пакета, используя проверенный ранее официальный бинарник и установленный OpenSSL:

```powershell
dart run tool/probe_traffic.dart <sing-box.exe> --tls <openssl.exe>
```

Приватные ключи не передаются в аргументах и не сохраняются в репозитории. OpenSSL вызывается напрямую с массивом аргументов, без shell. Системный proxy, TUN, firewall, службы и пользовательские профили не менялись. Остановка дочернего ядра по-прежнему выполняется завершением собственного процесса, не RPC Karing.

Этот результат подтверждает базовый VLESS/WebSocket/TLS с временным доверием и проверкой имени на localhost. Он не подтверждает публичные цепочки сертификатов, отзыв/истечение сертификата, uTLS, Reality, внешние серверы, UDP, TUN, полный набор режимов или транспорт службы Karing. Используется обычное ядро 1.13.0, а не отсутствующий модифицированный Karing core.

Следующий ограниченный шаг — проверить SOCKS CONNECT на том же стенде и затем передачу UDP отдельным сценарием. Восстановление Karing DNS batch/FakeIP и нативной службы остаётся в плане полной совместимости.

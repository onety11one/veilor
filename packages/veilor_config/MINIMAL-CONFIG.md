# Полный минимальный тестовый конфиг

Дополнение следующего этапа: [реальный запуск выявил ошибку DNS detour, которая исправлена; пройдены два цикла запуска/завершения](LIFECYCLE.md). Приведённые ниже результаты check относятся к этапу до runtime-проверки и не подтверждали запуск.

21 октября 2026: собраны log, DNS, loopback mixed inbound, direct/VLESS outbounds и route. Это отдельный тестовый сценарий, а не восстановленный полный генератор Karing и не новый билд приложения.

## Реализовано

- Один mixed inbound на `127.0.0.1`, явный порт 1024–65535, `set_system_proxy=false`. TUN, службы, автоматическая настройка прокси и Clash controller отсутствуют.
- Один VLESS-профиль с параметрами TLS/WebSocket из синтетической фикстуры. Проектор сохраняет поля профиля и удаляет метаданные, как на предыдущем этапе.
- Полный DNS из SingleServerDnsPlan. Direct/proxy теги проверяются на соответствие outbound. Resolver для имени VLESS-сервера задан в route.default_domain_resolver и использует прямой DNS роли outbound.
- Route.final указывает на VLESS; правило port=53/action=hijack-dns ограничено входом mixed_in_proxy. Это минимальная тестовая маршрутизация, не игровые/рабочие режимы и не пользовательские правила Karing.
- Структурный валидатор проверяет ссылки route/DNS/inbounds, дубликаты и пустые теги. Ошибки DNS отменяют выдачу конфига целиком.
- Неподдерживаемые протоколы, цепочки detour и переданный внешний domain_resolver отклоняются явно. Минимальная сборка не создаёт недостающие цепочки или endpoints.

Генератор не проверяет все возможные VLESS/TLS/transport поля — для них дополнительно нужен валидатор ядра. Проверка ссылок рассчитана на точную минимальную схему, а не произвольный пользовательский конфиг.

Формат сверен с официальной документацией [mixed](https://sing-box.sagernet.org/configuration/inbound/mixed/), [route](https://sing-box.sagernet.org/configuration/route/) и [rule actions](https://sing-box.sagernet.org/configuration/route/rule_action/). Это современные базовые форматы sing-box, не доказательство соответствия доработкам Karing.

Это обычное официальное ядро 1.13.0, а не установленное модифицированное Karing 1.13.19.2802 и не отсутствующее ядро 1.14.0 текущей исходной базы. Совместимость Karing batch/FakeIP/правил/служебного протокола этой проверкой не установлена.

## Воспроизведение

Из папки пакета:

```powershell
dart run test/minimal_config_test.dart
dart run test/dns_test.dart
dart run test/projection_test.dart
dart analyze lib test tool
dart run tool/write_test_config.dart <synthetic-output.json>
dart run tool/check_with_core.dart <путь-к-проверенному-sing-box.exe> <synthetic-output.json>
```

Итог: **15 тестов сборки + 23 DNS + 14 outbound = 52 теста прошли**, анализатор — **No issues found**. Дополнительно три случая проверки с реальным CLI дали ожидаемые результаты, приведённые выше. Повторный прогон старых тестов включает 6 сравнений с исполняемым историческим buildOutbound.

Сгенерированный файл текущего прогона находится в outputs/veilor-minimal-test-config.json относительно workspace. Он не предназначен для реального подключения и не устанавливался в приложение.

Следующий ограниченный эксперимент — отдельный запуск/остановка тестового ядра только с loopback inbound и проверкой его жизненного цикла. Затем потребуется восстановление Karing-специфичных DNS-возможностей и настоящего транспорта службы; текущий прототип не заменяет их и не подключён к UI.

# Контракт состояний VPN

Независимый Dart-пакет без внешних зависимостей. Содержит модель состояния и синхронную обработку событий для будущего интерфейса Veilor. Не подключён к приложению и не содержит нативного транспорта или команд управления VPN.

## Предлагаемая политика интерфейса

Это новый слой представления поверх наблюдаемого контракта, а не восстановленная реализация FlutterVpnService.

| Состояние, подтверждённое службой | Тоггл | Повторное нажатие | Время сессии |
| --- | --- | --- | --- |
| invalid / disconnected | Выключен | Запуск доступен | Не показывать как активное |
| connecting | Выключен, занят | Заблокировано | Не показывать как активное |
| connected | Включён | Остановка доступна | Можно показать при наличии свежего startTime ядра |
| reasserting | Занят | Заблокировано | Не показывать как активное |
| disconnecting | Занят | Заблокировано | Не показывать как активное |
| unknown / неподтверждённое | Не утверждать подключение | Заблокировано до синхронизации | Недоступно |

Во время локальной операции нажатие заблокировано независимо от последнего состояния службы. Успех команды сам не создаёт connected/disconnected. Если за время операции не было нового наблюдения, нужен повторный currentState. Начальное состояние unknown устраняет предположение, что при открытии окна VPN обязательно выключен.

Ошибка хранится отдельно от фазы. Индикатор красный при известной ошибке, зелёный при подтверждённом connected без ошибки, нейтральный в остальных случаях. Отключение само по себе не означает ошибку. Ошибка остаётся после disconnected, чтобы сообщение о неудачном запуске не исчезало из-за cleanup. Она очищается при новой попытке, явном закрытии сообщения или переходе в connected. Ошибка чтения состояния сбрасывается после следующего наблюдения. Красный индикатор при ошибке остановки может сочетаться с подтверждённым connected: VPN мог остаться работающим.

Состояние оплаты/подписки не включено в состояние службы. Оно может блокировать действие на уровне продукта, но не доказывает остановку уже работающего VPN. Отказ HTTP-метрик также не является событием отключения службы.

## Будущее подключение к backend

1. Подписаться на события службы, затем вызвать currentState с токеном `beginStateRead()`. Callback направлять в `observe()`, ответ запроса — в `completeStateRead()`. Запоздавший ответ или ошибка запроса не перезапишут более новое событие. Протокол доставки самого плагина ещё требуется проверить.
2. Перед запуском/остановкой получить `beginOperation()`. При отказе не выполнять команду. Токен завершать в обработчике результата/исключения через `completeOperation()`; повторное завершение игнорируется. Это только учёт операции, сам вызов службы находится снаружи.
3. Получать ошибки из явного результата backend. Не классифицировать их поиском слова timeout в произвольном тексте. Подробности для кнопки «Подробнее» передавать отдельным защищённым диагностическим слоем; reducer хранит только категорию.
4. Если после завершения `confirmed == false`, запросить состояние повторно. Нет автоматического polling или собственного таймера ожидания: deadline определяет будущий backend.
5. Время брать из свежего `/connections.startTime`, только когда `canShowSessionDuration` разрешён. Старый снимок прошлой сессии не переносить в новую. Если метрики недоступны, показывать отсутствие данных отдельно от состояния VPN.

Токены блокируют старые запросы внутри одной модели. Они не заменяют проверку порядка/потери событий, перезапуска службы и завершения stream в будущем реальном транспорте.

## Проверка

Из папки пакета:

```powershell
dart run test/state_test.dart
dart analyze lib test
```

21 октября 2026, Windows, Dart 3.12.2: **24 теста прошли**, анализатор — **No issues found**. Проверены нормальный запуск/остановка, restart/reload, отказ подготовки/операции/timeout, сохранение ошибки после cleanup, неподтверждённая остановка, неизвестные состояния, конфликт callback с начальным запросом, устаревшие/повторные/чужие токены и восстановление после ошибки чтения состояния.

Реальные операции VPN на этом этапе не запускались. Автотесты проверяют предлагаемый контракт на синтетических последовательностях; они не доказывают соответствие отсутствующего нативного пакета. Активные исходники приложения и установленный Karing не менялись.

Дальнейшие этапы конфигуратора и синтетического транспорта описаны в отдельных пакетах veilor_config и veilor_core_transport_lab. Реальное ядро Karing ещё не запускалось.

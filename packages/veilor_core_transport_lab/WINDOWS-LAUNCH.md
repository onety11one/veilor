# Подготовка Windows launcher

22 октября 2026. Реализован проверяемый план запуска и испытан на имитаторе. **Диспетчер реального karingService.exe не включён**: полная схема SDK-конфига и безопасная среда ещё не восстановлены. Это подготовка запуска, не готовый Windows VPN-билд.

## Что добавлено

`WindowsLaunchPlan.prepare()` создаёт уникальный каталог, файлы service.json/service_core.json и дочерние base/work/cache/logs. Все управляемые пути абсолютные; родительский каталог разрешается через resolveSymbolicLinks. Пользовательский профиль установленного Karing не читается.

| Поле service.json | Назначение в плане |
| --- | --- |
| base_dir | Собственный base |
| work_dir | Собственный work — текущий каталог тестового процесса |
| cache_dir | Собственный cache |
| core_path | Собственный service_core.json |
| log_path | logs/service_core.log |
| err_path | logs/service_error.log |

Дополнительные serviceOptions копируются через JSON, неизвестные поля сохраняются; переопределять шесть управляемых путей нельзя. Не-JSON значения отклоняются до создания ресурсов. Файлы закрываются/flush завершается до запуска. Пути строятся через URI, чтобы Windows-разделители и завершающий слеш не приводили к разным представлениям work_dir. Проверен настоящий запуск из пути с пробелами и кириллицей.

**Это частичный serializer.** Он не добавляет выдуманные id/version/secret/control_port и не утверждает, что остальные 25 наблюдаемых полей необязательны. В Karing work_dir указывал на assets; пустой приватный work стенда не заменяет необходимые assets. Содержимое произвольного core JSON и дополнительные поля не проходят полный аудит файловых/сетевых побочных эффектов: изолированы перечисленные пути, а не любой возможный профиль. Для реального запуска это остаётся обязательной работой.

## Аргументы и порты

План формирует отдельные аргументы, без shell и ручных кавычек:

```text
run2 --service-config <absolute-service.json>
     --service-http-port <nonzero-control-port>
     --connected-port <parent-listener-port>
```

JSON, secret и профиль в argv не помещаются. service-http-port не смешивается с полем service.json control_port или Clash API. Аргументы неизменяемые.

Оба loopback-порта сначала выделяются и удерживаются ОС. Parent listener остаётся открытым до очистки. Резерв управляющего порта освобождается непосредственно перед запуском дочернего процесса. **Между освобождением и bind остаётся гонка:** Karing не получил поддержку наследования сокета от этого плана. При занятом порте запуск должен провалиться, не превращаться в соединение с чужим контроллером. Этот случай проверен отдельным тестом: дочерний процесс не сообщает готовность и выходит, чужому HTTP-server запросы не отправляются.

Имитатор теперь поддерживает `fixedPortPlan: true`: получает заранее назначенный ненулевой порт, открывает именно его и отправляет TCP-уведомление. Stdout в этом режиме содержит обычную диагностику, не объявление порта, и только дренируется. После уведомления проверяется PID владельца слушателя; перед командами он проверяется повторно. Прежний режим с `--service-http-port 0` оставлен для прежних тестовых сценариев и не считается контрактом Karing. К аргументам имитатора добавлен его собственный --mock-scenario; реальный план его не содержит.

## Проверка файла и singleton

`auditExecutable()` **только читает файл**:

1. Разрешает реальный путь и сверяет SHA-256 с явно переданным ожидаемым хешем.
2. Проверяет базовый PE/x64/PE32+ заголовок. Это не полная проверка Windows loader, подписи или доверенности файла; тестовый PE fixture намеренно не исполняется.
3. Для первоначальной реализации допускает ASCII-имя .exe, чтобы не выдавать Dart lowercasing за полный Go EqualFold для Unicode.
4. Через Toolhelp32Snapshot и Process32FirstW/NextW проверяет совпадение базового имени среди работающих процессов. Полные argv, окружение и данные профилей не собираются, инвентарь не сохраняется. Совпадение блокирует план, даже если exe в другой папке. Повышения прав нет.

Для SHA-256 используется crypto 3.0.7, уже доступный в локальном SDK cache; установка зависимостей выполнена `pub get --offline`. Проверки процесса и файла — снимки: изменение файла, повторное использование PID/порта и появление конкурирующего процесса между проверкой и запуском полностью не исключены. Проверка файла до запуска плюс PID порта после запуска не равна атомарной аутентификации исполняемого образа. Для production это надо учитывать отдельно.

Read-only проверка ранее сохранённого karingService.exe 1.2.25+2802 с известным SHA-256 вернула **singletonConflict**. Хеш и заголовок прошли, но установленный Karing уже имеет процесс с таким именем. Файл не запускался. Результат сохранён в [launch-readonly-audit.json](../../research/windows-service-contract/launch-readonly-audit.json).

Документация Win32 ABI: [PROCESSENTRY32W](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/ns-tlhelp32-processentry32w), [снимки системы](https://learn.microsoft.com/en-us/windows/win32/toolhelp/snapshots-of-the-system), [Process32NextW](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-process32nextw). Используется Windows x64 layout: 568 байт, szExeFile со смещения 44; проверено чтением собственного имени процесса.

## Результат проверок

- **15 новых тестов плана**: сериализация, защита управляемых путей, порты/очистка, Unicode/пробелы, хеш и PE, конфликт имени, фиксированный порт без stdout-протокола, таймаут и занятый порт.
- **12 интеграционных тестов контроллера**, включая новый путь запуска: готовность не выдаётся за connected.
- **22 прежних интеграционных теста транспорта** проходят; всего на этом этапе выполнены 49 тестов лабораторного пакета. Чистая политика состояний на этом шаге не менялась.
- Dart analyzer — без замечаний. После проверок тестовые процессы и созданные каталоги убраны. Установленный Karing и активные lib/bind/windows/pubspec приложения не изменены.

Из каталога пакета:

```powershell
dart pub get --offline
dart analyze
dart test/launch_plan_test.dart
dart test/controller_test.dart
dart test/transport_test.dart
# Только read-only аудит известного snapshot, НЕ запуск:
dart tool/audit_known_core.dart <absolute-path-to-snapshot>
```

Последующее исследование нашло подтверждённых потребителей 9 из 25 наблюдаемых полей и добавило перенос выбранных .srs через bundledAssetsRoot в WindowsLaunchPlan.prepare. При отсутствии обязательного для профиля local asset источника подготовка завершается ошибкой. Подробности и оставшиеся пробелы — [CONFIG-AND-ASSETS.md](../../research/windows-service-contract/CONFIG-AND-ASSETS.md). Полная схема SDK всё ещё не восстановлена; наличие плана и зелёных тестов имитатора не снимает необходимость изолированного runtime-теста.

## Уточнение AOT Windows startup

В [WINDOWS-PATHS-STARTUP.md](../../research/windows-service-contract/WINDOWS-PATHS-STARTUP.md) подтверждены пути и порядок запуска исходного Karing. Его argv использует --option=value, тогда как лабораторный план пока передаёт пары --option value; принятие обоих вариантов настоящим core динамически не проверено. Оригинальный Process.start использует каталог exe как workingDirectory; work_dir в service JSON отдельно указывает на assets. Папки лаборатории изолированы намеренно и не объявляются точной раскладкой оригинала. Исследование не является разрешением запускать настоящий core рядом с работающим VPN.

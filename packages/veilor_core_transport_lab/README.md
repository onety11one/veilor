# Стенд транспорта Windows core

22 октября 2026. Отдельный Dart-пакет без Flutter; зависимости — локальная veilor_vpn_state и crypto 3.0.7 для SHA-256. Реализует и проверяет жизненный цикл **синтетического дочернего процесса**, не запускает karingService.exe и не подключён к UI.

## Что работает

`MockCoreSession.start()` сначала открывает parent listener на `127.0.0.1`, затем запускает локальный `tool/mock_core.dart` напрямую через `dartvm.exe` из подготовленного SDK, без shell. Windows CLI `dart.exe` в этом SDK создаёт отдельную VM: прямой запуск нужен, чтобы владелец сокета совпадал с PID созданного Process. Каждый экземпляр получает собственный временный каталог и синтетический service.json. Аргументы сохраняют исследованную форму `run2`, `--service-config`, `--service-http-port`, `--connected-port`.

Стенд ждёт объявления HTTP-порта и TCP-уведомления; завершение процесса до готовности и таймаут считаются ошибками с очисткой. Обе выходные трубы читаются; содержимое диагностик не сохраняется. Публичные ошибки содержат категорию, без конфигов и ответов сервера.

`reload()` отправляет GET `/reload/`; `stop()` — GET `/stop/` и обязательно ждёт завершения собственного процесса. Если остановка не завершилась вовремя, стенд завершает только созданный им Process и ждёт его выхода. Повторные stop используют один Future. После остановки закрываются listener/HTTP-client и удаляется собственный временный каталог.

HTTP использует только loopback, обходит системный proxy, запрещает redirects, ограничивает время и размер ответа (16 KiB). При запуске и перед каждым запросом `WindowsPortOwner` сверяет PID слушателя `127.0.0.1:port` с нашим Process через read-only Windows API [GetExtendedTcpTable](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedtcptable) и [MIB_TCPROW_OWNER_PID](https://learn.microsoft.com/en-us/windows/win32/api/tcpmib/ns-tcpmib-mib_tcprow_owner_pid). Запросов PowerShell и повышения прав нет. Поддерживается Windows x64; отсутствие данных, чужой PID, wildcard и неоднозначность блокируют HTTP-команду. При неудаче stop очищается только собственный дочерний процесс.

HTTP 200 проверяется вместе с JSON: успешный reload требует явных `err: null, extra: null`, stop — `err: null`. Строковый err означает отказ команды; отсутствие/неверный тип полей и повреждённый JSON считаются некорректным ответом. Текст ошибки и extra не попадают в публичное исключение. Основание и границы — [статический разбор ответов](../../research/windows-service-contract/COMMAND-REPLIES.md).

## Где стенд отличается от Karing

- `MockCoreSession` не принимает произвольный exe. Точка входа тестов находится в `test/`; разрешение пути mock-скрипта рассчитано на эту структуру. Сценарий foreignControl специально позволяет объявить порт тестового чужого listener: это проверяет запрет отправки команд. Это лабораторная реализация, не библиотека для встраивания в приложение.
- В старом режиме `--service-http-port 0` и JSON-объявление порта в stdout — **собственные расширения имитатора**. У исследованного Karing нулевой порт отключает HTTP-ветку. Добавлен `fixedPortPlan: true` с заранее назначенным ненулевым портом, без объявления через stdout — см. [WINDOWS-LAUNCH.md](WINDOWS-LAUNCH.md).
- В старом режиме синтетический JSON содержит только labOnly, в новом — также шесть управляемых путей и отдельный core JSON. Оба режима не заменяют полную VpnServiceConfig.
- Путь со слешем и HTTP 200 заданы имитатором. Нормализация URL, реальные status/body и авторизация Karing ещё не подтверждены динамически. Форма err/extra в двух обработчиках подтверждена статически, полная схема extra неизвестна.
- TCP-уведомление даёт `readySignalReceived`, **не** FlutterVpnServiceState.connected. Уведомление не аутентифицировано. Проверка PID слушателя — снимок состояния: остаётся окно между проверкой и соединением, возможны переиспользование порта/PID и другие гонки. Она уменьшает риск отправки команды чужому процессу, но не заменяет аутентификацию. Состояния VPN и UI к стенду не подключены.
- Нет TUN, proxy, firewall, автозапуска, установки Windows-службы, рестарта реального ядра или восстановления всех функций Karing.

## Проверка на Windows

```powershell
# Из каталога этого пакета, используя подготовленный Dart SDK:
dart pub get
dart analyze
dart test/transport_test.dart
```

Каждый тест запускает настоящий отдельный Dart-процесс с локальным HTTP-server, а не подменяет Process в памяти. Установленный Karing не используется. Эти проверки подтверждают поведение нашего стенда; они не подтверждают совместимость с бинарником Karing.

Связь наблюдения процесса/ошибок с veilor_vpn_state добавлена в `LabVpnController`: 12 интеграционных тестов и 14 тестов политики, без реального источника VPN callback. Готовность TCP не становится connected. Политика и ограничения — в [TRANSPORT.md](../veilor_vpn_state/TRANSPORT.md). Прежние 22 транспортных теста сохраняются; план запуска добавляет ещё 15.

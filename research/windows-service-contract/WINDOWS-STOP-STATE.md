# Windows: остановка, завершение процесса и события состояния

22 октября 2026. Offline-разбор сохранённого Karing 1.2.25+2802. Продолжает [пути и запуск](WINDOWS-PATHS-STARTUP.md). Это статический контракт, не успешная остановка настоящего VPN. Код службы не запускался, запросы не отправлялись, proxy не менялся.

## Остановка

PC.stop устанавливает operation slot 0x4290, вызывает зарегистрированный state callback, затем ожидает Future.any из выполнения _stop через FlutterVpnWait.wait и внешнего таймера **8 секунд**. После результата operation slot очищается; дальнейший callback зависит от результата. _stopWithoutUpdateState также ждёт _stop/timeout, но не содержит такого же внешнего уведомления состояния; duration передаётся ему вызывающим кодом.

Внутренний PC._stop:

1. Читает service HTTP port 0x4280. Если он ненулевой, вызывает HttpRequest.request с action `stop` и Duration **200 мс**, затем ожидает возврат.
2. Сбрасывает started flag 0x4268, получает basename пути service exe.
3. Если есть сохранённый Process, сохраняет его PID и ожидает Future.any из waitProcessExit и внутреннего таймера **10 секунд**.
4. После этого вызывает Process.killPid для сохранённого PID и очищает ссылку Process в slot 0x4260.
5. Вызывает _killProcesses с полученным именем. Если Process изначально отсутствует, переход к этому helper тоже есть.

_killProcesses перечисляет Windows-процессы, сравнивает преобразованное имя с переданным именем и вызывает _killPid для совпавших записей. Точную семантику динамически вызываемого преобразования/сравнения регистра здесь ещё не восстановили. Однако охват явно шире собственного child Process: эту ветку нельзя запускать на рабочей машине с действующим Karing.

8 секунд внешнего ожидания и 10 секунд внутреннего — разные уровни. Сам Future.any не доказывает отмену проигравшей операции. Также вызов kill/очистка ссылки не доказывают, что процесс уже завершился: дополнительное ожидание после финального kill в просмотренной ветке не подтверждено. Некоторые ветки переписывают результат в общий успешный enum; считать это доказательством полного восстановления сети нельзя.

В этом шаге подтверждены action и переданный duration. Полные HTTP method, URL, авторизация, обработка тела ответа и ошибки требуют отдельного разбора HttpRequest.request. Duration 200 мс не объявляется единственным end-to-end timeout всего HTTP-запроса.

## Завершение процесса и query состояния

Подписка на exitCode после успешного запуска связана с closure 0xd86264 (точная pool-запись 0x30a20). Callback очищает Process и started flag. Если operation slot 0x4290 занят, отдельное уведомление о выходе подавляется; если свободен и callback зарегистрирован, отправляется событие с данными exit code.

PC._currentState выбирает enum по наличию ссылки Process (slot 0x4260). Здесь не видны ни запрос трафика, ни проверка очистки proxy/маршрутов. Имена enum не угадывались по их индексам: сохранены ссылки на конкретные объекты и инструкции. Восстановление полного отображения enum и верхнего state API ещё требуется.

Следствие для Veilor: нужно различать намеренную операцию остановки, неожиданный выход и устаревший callback прежней сессии. Ссылка на процесс или HTTP 200 не заменяют подтверждение результата. Лабораторная модель уже учитывает часть этих различий, но реальный transport к ней не подключён.

## Системный proxy — отдельный этап

VPNService.stateCallback сравнивает входное состояние с конкретным enum объектом (pool 0xd318). В этой ветке запрашивает getSystemProxyEnable и при true ожидает FlutterVpnService.cleanSystemProxy. PC.cleanSystemProxy вызывает MethodChannel.invokeMethod с именем `cleanSystemProxy`.

При исключении в этой очистке есть catch/log, после которого выполнение всё равно переходит к списку VPNService.onEventStateChanged и передаёт событие слушателям. Поэтому факт получения события не доказывает успешное восстановление proxy. Native dispatcher ранее найден, но успешное выполнение WinAPI и фактическое состояние сети здесь не проверялись. Очистку TUN, маршрутов, DNS, firewall и полный список side effects этот callback не закрывает.

## Проверка

verify-stop-state.py проверил **48 точных инструкций**, три Duration-константы в двух предыдущих pool dumps, action `stop`, имя native method и привязку exit callback. Snapshot проверяется по закреплённому SHA-256. Выбранные диапазоны дизассемблируются из ELF без запуска VM. Повторный результат должен быть идентичен.

- [windows-stop-state.json](windows-stop-state.json): машинно читаемый контракт и ограничения.
- [windows-stop-state-x64.txt](windows-stop-state-x64.txt): выбранные инструкции; строки вне allowlist маскируются.
- inspect-config-callers.py, verify-stop-state.py: копии для review; рабочие оригиналы в work/karing-feasibility. Для воспроизведения нужны pinned snapshot/dumps/SDK-структура и Python-зависимости. Из research без восстановления структуры не запускать.

Raw pool строки не всегда являются JSON-литералами: экспортёр теперь маскирует такие записи вместо попытки разобрать их как JSON. Произвольные адреса/значения объектов из pools не публикуются; имена функций из pool сами по себе не используются вместо проверки точных call targets/closure.

## Что делать дальше

Проверить HttpRequest.request и точные enum/state API, затем составить единую таблицу lifecycle с отдельными подтверждениями остановки процесса и очистки сети. После этого переносить только подтверждённые операции в Windows backend и испытывать его в отдельной VM. Не копировать в Veilor завершение процессов по одному имени и не объявлять любой cleanup успешным. Политика sentry_minversion, полный генератор core JSON и паритет версий остаются открытыми.

Активные lib/bind/windows/pubspec и установленный VPN не менялись. Production backend и готовая Windows VPN-сборка пока не созданы.

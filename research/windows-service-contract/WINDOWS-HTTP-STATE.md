# Windows: HTTP-контракт и имена состояний

22 октября 2026. Исследованный бинарник — Karing 1.2.25+2802. Продолжает [stop/state](WINDOWS-STOP-STATE.md). Установленный Karing и его ядро не запускались; HTTP-команды им не отправлялись.

## Управляющий HTTP

Выбранный путь HttpRequest.request → специализированный HttpClient.open → _openUrl подтверждает метод **get**, схему **http**, host **127.0.0.1** и переданный вызывающим кодом порт. В отдельном selector возвращается **DIRECT**. Нельзя смешивать этот API с Clash API, где ранее найден отдельный control_port/secret.

Action дополняется знаком вопроса и при наличии query-параметров — их строковым представлением. В Blutter question mark записан как C++ escape `\?`; это не JSON escape и не обратная косая черта в URL. Точная обработка/экранирование всех query-параметров ещё не проверена.

Вызов SDK HttpClient.open разбирает query и создаёт Uri. Чистая локальная проба с синтетическим port 12345 и action stop дала **http://127.0.0.1:12345/stop**, без trailing slash и без пустого query в строке. Проба не использует HttpClient или сеть. Таким образом исходный Flutter-запрос и известный native handler `/stop/` нельзя объявлять одним и тем же начальным URL: нормализация/redirect/совместимость требуют отдельной проверки сервера. Лаборатория пока обращается прямо к `/stop/` и запрещает redirects; это осознанное отличие, не доказанный паритет.

Обработчик требует HTTP **200** (в AOT сравнение Smi с 0x190). Затем декодирует поток UTF-8, вызывает Stream.join и возвращает текст. Ошибка статуса, timeout/null response и исключения идут в ошибки/закрытие клиента. На этом уровне **JSON не разбирается**. _stop после ожидания request не проверяет возвращённое тело, поэтому JSON `err` сам по себе не доказывает, как оригинал обработает отказ остановки. Наша отдельная command_reply-проверка строже; сохранять эту границу при интеграции.

Ранее найденные 200 мс передаются запросу и используются в response race. Открытие запроса ожидается до этого race, а join тела не имеет явного собственного таймера в выбранном диапазоне. Нельзя трактовать 200 мс как доказанный единый end-to-end deadline. Явная настройка Bearer header в просмотренном пути не найдена; это не динамический аудит всей авторизации/redirect-политики.

## Точная карта enum

Раньше были известны только индексы. Анализатор дополнен узкой выгрузкой двух известных class ID: 8311 и 8310. Индекс берётся из native int64 поля 0x08, имя — из String поля 0x10. Положение имени независимо видно в enumToString; CID проверяется, имя ограничено ASCII identifier, никакой Dart-метод enum не вызывается.

| FlutterVpnServiceState | Индекс |
| --- | --- |
| invalid | 0 |
| disconnected | 1 |
| connecting | 2 |
| connected | 3 |
| reasserting | 4 |
| disconnecting | 5 |

| VpnServiceWaitType | Индекс |
| --- | --- |
| processExit | 0 |
| timeout | 1 |
| err | 2 |
| done | 3 |

Получены 10 записей. В первой успешной выгрузке колонка poolOffset содержала displacement относительно tagged pointer; в windows-http-state.json он нормализован **+1**, чтобы совпадать с прежним pp.txt. Позднейшая версия экспортёра печатает сразу нормализованный offset. В новом документе используются нормализованные значения.

## Как состояния связаны с ранее найденными ветками

- start публикует connecting; после успешного _start — connected.
- stop публикует disconnecting; при результате done — disconnected; при другом исходе запрашивает _currentState.
- PC.currentState сначала возвращает operation state из slot 0x4290, если он есть; иначе вызывает _currentState. Поэтому предыдущий вывод о проверке одной Process-ссылки относится только к внутреннему _currentState.
- _currentState возвращает connected при наличии ссылки Process, иначе disconnected. Это не независимая проверка трафика или сохранности сети.
- Неожиданный exit очищает Process/started и публикует disconnected, если не идёт другая операция.
- VPNService.stateCallback выполняет ветку proxy cleanup именно для disconnected; после неё передаёт событие подписчикам, в том числе после пойманного исключения очистки.
- invalid и reasserting найдены как значения, но полный набор их переходов этим шагом не восстановлен. Restart и связь состояний с UI ещё требуют проверки.

## Стабильность инструмента: открытая проблема

Enum получены **в одном успешном запуске** собственной VM анализатора на сохранённом snapshot. После небольшого исправления формата колонки offset два следующих запуска завершились **0xC0000005** после маркера Dart_CreateIsolateGroup, до enum-выгрузки. Причина не установлена. Такой сбой уже был и на предыдущем этапе до добавления enum-кода; это не позволяет назвать точную причину или исключить другие дефекты инструмента.

Успешный результат проверен против известного layout, CID, enumToString и объектов в прежнем pool, но **повторяемость извлечения имён из VM пока не подтверждена**. Повторяемые offline-проверки сохранённого результата не заменяют второй успешный VM-run. Не продолжать бесконечные перезапуски; перед дополнительными VM-исследованиями локализовать crash. Это проблема анализатора, не доказательство падения самого Karing.

## Артефакты и проверка

verify-http-state.py выполняет 26 точных instruction checks, сверяет выбранные строки с двумя старыми dumps и валидирует 10 enum-записей успешного запуска. windows-http-state.json содержит небольшие receipts всех трёх enum-запусков и SHA-256 инструмента/входа.

- [windows-http-state.json](windows-http-state.json): контракт, enum, checks и ограничения.
- [windows-http-state-x64.txt](windows-http-state-x64.txt): выбранные инструкции с маскированием строк вне allowlist.
- blutter-vpn-enums.patch: изменение анализатора поверх ранее сохранённого diagnostic patch; исходники формата Dart не менялись.
- verify-http-state.py, inspect-config-callers.py, probe-http-uri.dart: копии для review. Рабочие оригиналы привязаны к work/karing-feasibility; нужны сохранённые dumps и SDK-зависимости. Из research без восстановления структуры не запускать.

Создание VM со snapshot может выполнять внутренние stubs, поэтому enum-выгрузка не называется чисто статической. App main не вызывается, attach к работающему процессу нет. Полные pools не публикуются.

Следующий полезный шаг: свести подтверждённые HTTP/state переходы в проверяемый контракт backend и проверить неблагоприятные сценарии на собственном имитаторе, включая ошибки остановки и proxy cleanup. Перед новыми VM-запусками диагностировать crash. Полный core JSON, версия/телеметрия, системная интеграция и испытание реального VPN всё ещё не закрыты.

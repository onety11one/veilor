# Изоляция Windows core и поля service.json

22 октября 2026. Проверка сохранённого бинарника Karing 1.2.25+2802, SHA-256 `023ed74fa5015aacf09d83ac7d4a80f9d48dbc0459018e8d75303d7d80d6a9ea`. Это статический разбор инструкций, без запуска core и без управляющих запросов установленному Karing. Выводы нельзя автоматически переносить на core 1.14.0.

## Главный результат

**Другой каталог с тем же именем karingService.exe не обеспечивает изоляцию.** `main.makeProcessSingleton` сравнивает базовые имена файлов без учёта регистра и пытается завершить совпавший процесс. Возможен обрыв уже работающего Karing.

В `main.makeProcessSingleton` (0x141607980) видна последовательность:

1. Получить свой PID, свой путь через `getResolvedExePath`, затем взять `filepathlite.Base`.
2. Перечислить процессы через Toolhelp32Snapshot / Process32First / Process32Next; пропустить собственный PID.
3. Преобразовать ExeFile другого процесса из UTF-16, применить Clean и Base.
4. Сравнить имена через `strings.EqualFold` (0x141607b85).
5. При совпадении вызвать `main.terminateProcess` (0x141607bc0).

`getResolvedExePath` запрашивает ExeWithContext, абсолютный путь и разрешает symlinks, но затем singleton отбрасывает каталог. `terminateProcess` (0x141607da0) сначала вызывает TerminateWithContext; при ошибке — KillWithContext. Дополнительной проверки полного пути внутри этого helper нет. Это попытки завершения, а не гарантия успешного завершения: права и ошибки ОС сохраняют значение.

Отдельное уникальное имя исполняемого файла уменьшает именно этот конфликт, но **не доказывает полную безопасность запуска**: остаются действия подготовки, конфиги, порты, файловые записи и сетевые интерфейсы. Бинарник не переименовывался, не патчился и не запускался.

## Что подтверждено о service.json

`main.preRun` вызывает `libbox.SentryInit`, затем `main.setUpDir`, затем singleton. `setUpDir` разбирает JSON через fastjson; ошибку разбора возвращает. Это JSON-текст, полученный предыдущим этапом, а не передача имени файла непосредственно в JSON-parser.

| Поле | Установленное поведение | Что ещё неизвестно |
| --- | --- | --- |
| core_path | Читается как строка; пустое значение даёт явную ошибку ` : core_path is empty`; добавляется в список конфигурационных путей | Полная схема core-конфига и совместимость с текущей версией приложения |
| err_path | Читается как строка; передаётся StderrRedirect | Допустимо ли отсутствие на всём пути запуска; обработка ошибки перенаправления вызывающей стороной |
| base_dir | Читается как строка; передаётся в Setup | Все последующие потребители и допустимые defaults |
| work_dir | Читается как строка; передаётся в Setup | Все последующие потребители и допустимые defaults |
| cache_dir | Читается как строка; передаётся в Setup | Все последующие потребители и допустимые defaults |

В исследованной функции только для `core_path` найдена явная проверка непустого значения. **Это не означает, что остальные поля можно без последствий опустить.** `libbox.Setup` записывает параметры в глобальные переменные и вызывает `os.MkdirAll` дважды. `StderrRedirect` вызывает `os.OpenFile`, затем обработку/перенаправление stderr. Подготовка уже имеет файловые побочные эффекты, даже если VPN ещё не подключён.

Отдельная `SentryInitPrivate` содержит чтение `core_path`, `log_path`, `id`, `version`, `sentry_minversion`. Внешняя `SentryInit` имеет косвенный callback и fallback `os.ReadFile`. **На последующем этапе привязка callback к Private подтверждена через libbox.init.0 и общий global** — см. [CONFIG-AND-ASSETS.md](CONFIG-AND-ASSETS.md). Это подтверждает потребителя, но не обязательность всех прочитанных полей.

`libbox.NewService` создаёт контекст и daemon.NewStartedService; непосредственного разбора service.json в этой функции не найдено. `BoxService.Start` вызывает StartOrReloadService. Полную цепочку потребителей и defaults ещё нужно восстановить. Предыдущее сравнение 16 старых присваиваний с 25 полями установленного JSON остаётся наблюдением, не формальной схемой.

## Условия следующего испытания

Перед запуском потребуется отдельная среда Windows без работающего Karing, либо иная доказанная изоляция процессов и сети. В ней использовать собственные каталоги конфигов, кэша и логов, собственные loopback-порты и синтетический профиль. Начальный тест — без TUN, системного proxy, firewall и автозапуска. Учётные данные и профили пользователя переносить не нужно.

Локальный стенд с имитатором core подготовлен в [veilor_core_transport_lab](../../packages/veilor_core_transport_lab/README.md): 22 интеграционных теста запуска, уведомления connected-port, таймаутов, остановки, принадлежности порта и проверки ответов; анализатор без замечаний. Имитатор имеет собственное объявление HTTP-порта и не доказывает runtime-совместимость с Karing. Проверка PID — снимок, не аутентификация; для реального backend по-прежнему нужны точные состояния, динамическое подтверждение протокола и недостающие исходники приложения.

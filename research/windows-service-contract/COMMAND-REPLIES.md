# Ответы команд и владение управляющим портом

22 октября 2026. Статически исследован Karing 1.2.25+2802, SHA-256 `023ed74fa5015aacf09d83ac7d4a80f9d48dbc0459018e8d75303d7d80d6a9ea`. Управляющих запросов к установленному ядру не выполнялось. Runtime-совместимость и текущий core 1.14.0 не подтверждены.

## Подтверждённая форма ответа

| Обработчик | Ветка | Объект, передаваемый render.JSON |
| --- | --- | --- |
| main.createHttpServer.func1.1 (reload) | Ошибка отсутствует | `{"err":null,"extra":null}` |
| Тот же | Ошибка есть | err — строка из Error(); extra — вспомогательное возвращённое значение, полная схема неизвестна |
| main.createHttpServer.func2.1 (stop) | После отправки сигнала остановки | `{"err":null}` |

reload вызывает restartService (0x141608241), проверяет error-interface через `test rbx,rbx` / `je` и в успешной ветке обнуляет обе части interface-значений для ключей err и extra. В ошибочной ветке вызывает Error() через interface, runtime.convTstring и присваивает результат err. Точные длины ключей: 3 и 5 байт. stop обнуляет interface-значение err. В трёх местах вызывается go-chi/render.JSON.

**Ветка ошибки reload также запускает goroutine** через function value, указывающий на main.createHttpServer.func1.1.1 (0x141608440). Она вызывает time.Sleep с 1 000 000 000 наносекунд и отправляет событие в канал по адресу 0x143569da0 — тот же канал, что использует stop. Время фактического завершения и доставка HTTP-ответа не измерялись. Клиент должен продолжать наблюдать процесс после отказа команды; ответ не гарантирует, что процесс останется работать.

Эти выводы проверяет `verify-service-replies.py`: **25 статических утверждений**, результат `reply-static-verified.json`. Используются инструкции из service-disassembly.json и неизменённый PE snapshot. Конкретный HTTP status, нормализация слешей, middleware и сериализация всех возможных extra не восстанавливались на этом этапе.

## Изменение лабораторного транспорта

[veilor_core_transport_lab](../../packages/veilor_core_transport_lab/README.md) теперь проверяет HTTP 200 и консервативную схему JSON. Строковый err — отказ, некорректный/неполный ответ — отдельная ошибка. Неизвестный extra при успехе не считается подтверждённым успехом. Ошибки публичного API не содержат ответ сервера.

Имитатор проверяет также отказ с отложенным выходом (250 ms в тесте; это намеренное ускорение, не измеренный тайминг Karing). Полная карта FlutterVpnServiceState и семантика успешного подключения остаются неизвестными. Успешный reload не объявляет VPN подключённым.

Добавлена read-only FFI-проверка владельца слушающего сокета через Windows GetExtendedTcpTable, AF_INET и TCP_TABLE_OWNER_PID_LISTENER. Фильтруется ровно 127.0.0.1 и нужный порт; PID сверяется с живым Process при запуске и перед каждой HTTP-командой. Обработка размера буфера ограничена тремя попытками и 16 MiB; native-память освобождается в finally. Системная таблица не сохраняется и не выводится.

При разработке обнаружено несовпадение PID dart.exe и владельца порта — CLI данного SDK запускает отдельную VM. Имитатор переведён на прямой dartvm.exe. В production аналогичное соответствие потребуется установить для реального launcher, а не допускать любой дочерний PID по предположению.

Проверка PID не является аутентификацией: между снимком таблицы и соединением остаётся гонка; PID/порт могут переиспользоваться. Область этой реализации — Windows x64 и лабораторный процесс. Чужой/неизвестный владелец блокирует HTTP; stop в этом случае завершает только принадлежащий стенду Process. Тест с заменой listener после готовности проверяет, что новому владельцу не отправляется stop.

Документация Microsoft, использованная для Win32 ABI: [GetExtendedTcpTable](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedtcptable), [TCP_TABLE_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/iprtrmib/ne-iprtrmib-tcp_table_class), [MIB_TCPROW_OWNER_PID](https://learn.microsoft.com/en-us/windows/win32/api/tcpmib/ns-tcpmib-mib_tcprow_owner_pid), [MIB_TCPTABLE_OWNER_PID](https://learn.microsoft.com/en-us/windows/win32/api/tcpmib/ns-tcpmib-mib_tcptable_owner_pid).

## Проверка результата

22 интеграционных теста на синтетических дочерних процессах прошли; Dart analyzer — без замечаний. После тестов процессы стенда отсутствуют, установленный Karing продолжает работать с прежними PID. Активные lib/windows/bind/pubspec приложения не изменены. Коммит и push этого этапа не выполнялись.

Следующий ограниченный шаг: политика событий/ошибок между транспортом и veilor_vpn_state; затем реальный launcher и испытание в отдельной Windows-среде. Этот стенд ещё не заменяет vpn_service и не снимает остальные препятствия для полной сборки.
